Stop using JS for that: moving features from JS to CSS and HTML

Als je iets gaat bouwen moet je kijken hoe je het kan doen met de minst krachtige tool: HTML > CSS > JAVASCRIPT

  • Javascript is imperatief: heel breekbaar. Je zegt precies wat de browser moet doen.
  • HTML en CSS zijn declaratief: je geeft aan wat het eindresultaat moet zijn en de browser vult het in.
  • Je moet dus meer moeite stoppen in Javascript en het kost de browser ook veel meer moeite.
  • Maak het zo simpel mogelijk!

Afspraak: alles wat je maakt op het web moet blijven werken.

Maar inmiddels zijn er veel toegankelijkere en betere manieren.

<label> <input type="checkbox" /> My awesome feature </label>
  • Ook als je op de tekst klikt doet de checkbox het
  • input { appearance: none; }
  • Je zorgt ervoor dat de browser het niet vormgeeft, maar dat je dit zelf kan doen.
  • Wordt soort div qua rendering
  • display: none; haalt het element weg. appearance: none; geeft aan dat hij niet ingevuld/vervangen wordt.
  • Input achtergrond
  • ::before bolletje
  • input::before { content: ' '; }
  • Pseudo-element wordt alleen maar getoond als er tekstuele inhoud is.
  • :checked { background-color: green; }
  • :checked::before { transform: translateX(1rem); }

Focus styling

  • Aangeven met welk element je interactie hebt als je je toetsenbord gebruikt.
  • input:focus { outline-color: transparent; }
  • Maar je moet dan wel iets terugplaatsen!
  • input:focus-visible { outline: 2px solid dodgerblue; }

Safari

  • <input type="checkbox" switch>
  • Maar nog niet op alle browsers

In-page transitions

html { scroll-behavior: smooth; }
  • Browser neemt al het werk uit je handen
  • Browser kan rekening houden met hoe krachtig het apparaat is
window.scrollTo({ behavior: "smooth" });
@media (prefers-reduced-motion: no-preference) { html { scroll-behavior: smooth; } }
  • Scroll margins bij fixed headers
#my-target { scroll-margin-top: 100px; } #my-target:target { outline: 10px solid deeppink; transition: 1s ease-in-out outline; }

Accordions and modals

<details open> <summary>Title</summary> <p>Tekst</p> </details>
  • open attribute wordt live beheerd door de browser
summary::marker { font-size: 1.5em; content: '🥰'; } [open] summary::marker { content: '🌶️'; }
summary:hover { cursor: pointer; background: deeppink; }
<dialog> <form method="dialog"> <h1>Title</h1> <button>sluit</button> </form> </dialog>
  • dialog wordt getoond via JavaScript of showModal()
  • Wordt op de top layer getoond
dialog { @starting-style { transform: scale(0.8); } }

Form controls

input, textarea { field-sizing: content; }
  • Field is precies even groot als de content
<select> <option>Option 1</option> <option>Option 2</option> <option>Option 3</option> </select>
select, ::picker(select) { appearance: base-select; }
  • Customizable select (Chrome)
  • Picker = dropdown element
<select> <button> You chose: <selectedcontent>Fire</selectedcontent> </button> </select>
:open::picker(select) { /* styles */ } select option { /* styles */ }

De geschiedenis van browsers

JavaScript is officieel geen onderdeel van de browser.

  • De meeste browsers gebruiken de JavaScript engine van Google.
  • Dus een andere engine dan de browser zelf.
  • Dit is om JavaScript als programmeertaal te verbeteren.

DOM en AOM

De DOM verandert mee met wat je aanpast met JavaScript.

AOM is bedoeld voor assistive technologies zoals screenreaders.

  • Zelfde als DOM plus extra informatie
  • Bijvoorbeeld aria-labels

Parsers

Een parser is een stukje programma dat een string neemt en deze interpreteert.

  • Voor HTML, CSS en JS
  • CSS wordt verwerkt via een CSS parser en daarna doorgegeven aan de style engine

Layout veranderingen

Kijk uit met veranderingen van de layout!

  • Media queries zijn oké
  • Verder liefst zoveel mogelijk vermijden
  • Browser kan het wel, maar het is zwaar

Rendering engine

De rendering engine is in feite alles behalve de JS engine en de interface.

  • Interface = waar dingen zich bevinden in de browser
  • JavaScript vraagt de DOM of iets bestaat en past het daarna aan
  • Grootste rendering engine: Blink (Chromium)
  • Wordt gebruikt door Chrome, Edge, Opera, Vivaldi
  • Ze interpreteren HTML, CSS en DOM op dezelfde manier

(JS) Core maakt JavaScript een programmeertaal.

Render blocking

Render blocking betekent dat de browser wacht met het verder verwerken van HTML totdat andere zaken klaar zijn.

  • HTML wordt eerst geparsed en geïnterpreteerd
  • Grote JavaScript pas later uitvoeren
  • Async en defer:
    • Async: voert JS uit wanneer het klaar is, volgorde niet gegarandeerd
    • Defer: eerst HTML verwerken, daarna JS
  • Defer scripts vaak onderaan de HTML zetten
  • Gebruik: script defer src of script async src
  • CSS eerst, daarna HTML, daarna JavaScript

Backward compatibility

Alles wat een browser ooit heeft ondersteund moet hij voor altijd blijven ondersteunen.

  • form.elements wordt nog steeds ondersteund
  • frameset is vervangen door iframe

Geschiedenis van browsers

  • Allereerste webbrowser: WWW Browser
  • Netscape (1994): eerste echte browser → Firefox (2004)
  • Internet Explorer (1995): eerste gratis browser
  • IE 5 Mac (2000): eerste browser voor Apple
  • Konqueror (2000) → Safari (2003)
  • WebKit is de rendering engine van Safari en open source gebleven
  • Safari iOS (2007): eerste iPhone browser met touch events
  • Chrome (2008): begon met WebKit, later Blink engine

IP-adres

Een IP-adres zorgt ervoor dat de browser weet waar hij naartoe moet op het internet.

Figma gebruiken voor websites

Figma wordt gebruikt voor het maken van websites.

  • Wat je in Figma doet komt vaak precies overeen met wat je in CSS zou doen
  • Het kan dus helpen bij het ontwerpen van websites
  • Auto layout in Figma is vergelijkbaar met flexbox in CSS

Figma is (en was) een tool die de manier waarop we websites ontwerpen heeft veranderd.

  • Alles wat je in Figma kunt maken, kun je ook op het web bouwen
  • Er was een gevoel dat alle websites er hetzelfde uitzagen

Design principe

Bij het ontwerpen moet je kijken naar verhoudingen in plaats van pixels.

  • Focus op de ratio tussen elementen
  • Niet alleen op exacte pixelwaardes

Video gebruikt veel data, maar door gebruik te maken van afbeeldingen in stop-motion kun je nog steeds een bewegend element maken dat een beetje op video lijkt.

/* stop-motion animation (instead of using video) */ div { animation: stop-motion 3s steps(31, end) infinite; }
  • In essentie is het een lange strip die over het scherm beweegt
  • Door steps(31, end) springt de animatie van frame naar frame
  • Daardoor krijg je een “stotterend” effect zoals stop-motion

Before subgrid: je kon alleen direction en layout toepassen op de grid zelf → niet op nested elementen.

Met subgrid kun je de rows en columns van een parent grid hergebruiken in een child element.

  • Je “erft” als het ware de grid van de parent
  • Handig voor consistente layouts in complexe interfaces

View Transitions

View Transitions worden gebruikt om vloeiende animaties te maken tussen pagina’s. In plaats van een harde page reload, animeert de browser de overgang automatisch.

  • Bijvoorbeeld bij het wisselen van taal (Engels ↔ andere taal)
  • De browser regelt de animatie zelf

bonabry.de gebruikt veel view transitions in hun website.

View Transitions op één pagina

Je kunt view transitions ook op dezelfde pagina gebruiken om tussen twee states te animeren. Hiervoor heb je wel een beetje JavaScript nodig.

Opbouw van formulier: voorwaarden

  • Introductietekst
    • Zeg erbij wat de gebruiker nodig heeft (bijvoorbeeld BSN)
  • Gebruiker kan voor inzending de ingevoerde waardes controleren, wijzigen of ongedaan maken
  • Na “volgende” of “verzenden” verschijnt een samenvatting van alle fouten

Introductietekst

  • Duur voor het invullen kan genoemd worden
  • Maar dit verschilt sterk per gebruiker, dus vaak niet handig

Automatisch invullen

  • Dingen die vaker ingevuld moeten worden automatisch invullen
  • Minder typefouten en prettiger voor de gebruiker

Verplichte velden

  • Duidelijk aangeven welke velden niet verplicht zijn
  • Bespaart onnodige energie

Foutafhandeling

  • Lijst met fouten tonen na submit
  • Linken naar het veld zodat gebruiker direct kan corrigeren
  • Bovenaan of bij het veld zelf tonen (of allebei)
  • Button pas activeren wanneer fouten opgelost zijn

Controlepagina

  • “Controleer uw gegevens” direct bewerkbaar maken
  • Knoppen: opslaan en later verder, of stoppen met formulier

Bevestiging

  • Bevestiging dat alles goed is gegaan
  • Wat zijn de vervolgstappen?
  • Wat kan de gebruiker verwachten?
  • Eventueel PDF download van inzending

Inhoud van formulier

  • Geen jargon of onduidelijke afkortingen gebruiken

Fouten in formulieren

  • Email herhalen is vaak onnodig
  • Laat gebruikers liever inloggen zodat data bekend is
  • Geslacht vragen is vaak niet nodig

Toegankelijkheid & touch targets

  • Componenten minimaal 44px x 44px
  • Gebruik min-width en min-height: 44px

Foutweergave

  • Niet alleen een rand om input
  • Ook duidelijke visuele markering naast veld

Design van formulieren

  • Buttons consistent en links uitgelijnd
  • Voortgang tonen boven formulier
  • Duidelijke stap-indicator
  • Verzendstap expliciet maken
  • Alle buttons overzichtelijk onderaan
  • Labels boven invoervelden
  • Verplicht/niet verplicht altijd tekstueel aangeven

Form flow

  • Logische volgorde aanhouden
  • Hulp aanbieden (chat, telefoon, email)
  • Hulp plaatsen in intro, footer en controlepagina

Labels en beschrijvingen

  • Uitleg niet in label zetten
  • Label kort en duidelijk houden
  • Gebruik aria-describedby voor extra uitleg
  • Meerdere id’s kunnen gekoppeld worden

Makkelijk invullen

  • Knippen en plakken toestaan
  • Bekende gegevens vooraf invullen
  • Autocomplete gebruiken
  • Goede spacing en 44px touch targets

Beschrijvingen

  • Uitleg boven formulier of sectie plaatsen
  • Structuur: label → uitleg → fout → input

HTML & CSS details

  • bdi translate="no" voorkomt vertaling van gebruikersinput
  • Gebruik inline-size en block-size in plaats van width/height
  • Gebruik inline-start voor logische layout

Validatie

  • Regels vooraf duidelijk maken
  • Uitleg over verplichte velden bovenaan
  • Geen onnodige min/max restricties
  • Foutmeldingen moeten uitleg geven

Focus & toegankelijkheid

  • Focus altijd duidelijk zichtbaar bij tabben
  • Niet continu foutmeldingen tonen
  • Foutmelding tonen op juist moment

Screenreaders

  • Gebruiker moet weten waar hij gebleven is
  • Bevestiging na submit duidelijk laten voorlezen
  • Positieve statusberichten automatisch laten voorlezen

Structuur

  • Form begint pas bij echte invoer (bijv. naam)
  • Context en uitleg buiten het form-element plaatsen

Soms had ik wel het gevoel alsof ik achterliep t.o.v. de rest, maar ik moet mezelf ook niet vergelijken. Van tevoren wist ik dat ik een stukje JavaScript in te halen had. Veel nieuwe dingen als API gebruiken, maar ook weer opfrissen van oude kennis en me daar dan weer verder in verdiepen. Ik vind de uitleg van docenten goed te volgen en ik merk dat me dit echt verder helpt. Veel aantekeningen maken, maar vooral mee typen helpt merk ik. Wat betreft mijn leerdoelen ben ik over één leerdoel nog niet helemaal uit en dat is of dit het vakgebied is voor mij. Ja, ik vind inmiddels coderen leuk en ik zie het echt als een grote meerwaarde dat ik dit kan, maar ik ben nog steeds een enorm visueel ingesteld persoon en ik mis dingen "maken" wel.
